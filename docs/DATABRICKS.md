# Databricks setup

These source notebooks have been executed for real in a Databricks Free Edition workspace (Glen's, 22 September 2026; see STATUS.md for the full record). Steps 1-6 below are verified to work as written; steps 7 onward remain untried.

1. Create or open your Databricks Free Edition workspace.
2. Upload the `heataction` package directory into a project folder, preserving the Python files and their names. Import `notebooks/01_ingest_databricks.py` as a Python source notebook. The notebook needs the package's parent directory in its `project_root` widget. Verified: `databricks workspace import-dir` uploads the package as plain workspace *files* (not notebooks), which stay importable via `sys.path`.
3. Enter that absolute `/Workspace/...` project folder in `project_root`. Choose a catalogue in which you can create schemas. The default is your current catalogue. Verified: the Free Edition default catalogue is named `workspace`, and no cluster needs to be created manually — the serverless job/warehouse compute the workspace ships with is sufficient.
4. Leave `raw_dir` and `date` blank for a current API fetch. Run the notebook. It creates `heataction_bronze`, `heataction_silver` and `heataction_gold` schemas within your selected catalogue. Verified: a live run produced 30 WBGT and 89 rainfall Silver rows, matching the same counts as a same-day local `ingest` run.
5. Inspect source responses, normalized rows and quarantined records. Confirm both source names appear. Run a second time and verify Silver does not duplicate `(source, station_id, observed_at)`. Verified for the first run; the idempotent-rerun check itself was not repeated here.
6. Query the Gold `current_persistence_forecasts` view. Empty output may mean no readings satisfy the explicit 30-minute freshness policy. Do not fill it with synthetic observations to appear live. Verified: 30 fresh station rows, `model_version = persistence_v0_1`.
7. If outbound API requests are blocked, collect observed data on your computer, upload raw envelope JSON files into a managed Unity Catalog volume, and set `raw_dir` to that volume path. This is replay ingestion; disclose it. Preserve source timestamps. Do not use the synthetic demo cache here.
8. Once date retrieval and coverage have been validated, backfill a bounded historical range. The prototype collector accepts one date per invocation, so schedule a small controlled sequence rather than an unbounded job.
9. Import `02_evaluate_databricks.py`, set its project root/catalogue, and run it after sufficient history exists. It records comparisons in MLflow. It does not register or deploy a winning model automatically. Verified the failure path: with under 7 days of history, it correctly raises `ValueError: Collect at least 7 days of usable history...` rather than fabricating a report. Also fixed a real environment bug found by running it: the Free Edition runtime's preinstalled `typing_extensions` is too old for mlflow's `pydantic` dependency (`ImportError: cannot import name 'Sentinel'`); the notebook now pins `typing_extensions>=4.13` and calls `dbutils.library.restartPython()` after `%pip install`.
10. Create a Lakeflow Job for notebook 01 after manual execution succeeds. Confirm scheduling support, quota use and failure handling in your account. Avoid continuously running compute. Not yet done: this first deployment pass deliberately used one-time `jobs submit` runs (no Jobs UI entry, no retry, no ongoing compute) rather than a saved, scheduled Job.
11. Upload `data/reference/observed/` to a Unity Catalog volume (verified path: `workspace.heataction_bronze.reference`, created with `databricks volumes create` and populated with `databricks fs cp`). Import `notebooks/03_geography_and_plan_databricks.py`, set `project_root`/`catalog`/`reference_root` (the volume path), and run it after notebook 01. Verified: it writes `heataction_silver.area_demographics` (55 rows), `heataction_silver.pilot_mapping_audit` (3 rows), and `heataction_gold.area_priority_plan` (3 rows, using `heataction.planner.build_plan` directly — the same function the local app calls, not a reimplementation). If every pilot area is stale/missing at run time, `forecast_wbgt`/`priority` are `None` for every row; the notebook writes with an explicit `StructType` schema for exactly this reason, since Spark cannot infer a type from an all-null column.
12. Build and deploy a Databricks App from `databricks_app/` (`app.py`, `app.yaml`, `requirements.txt`) with `databricks apps create <name>` then `databricks apps deploy <name> --source-code-path <workspace path>`. It authenticates as its own service principal (`databricks.sdk.core.Config`, credentials injected automatically as `DATABRICKS_CLIENT_ID`/`DATABRICKS_CLIENT_SECRET`, no user token) and reads `heataction_gold.area_priority_plan` over `databricks-sql-connector`. Grant that service principal `CAN_USE` on the SQL warehouse (`databricks warehouses update-permissions`, additive — not `set-permissions`, which replaces the whole ACL) and `USE`/`SELECT` on the Gold/Silver schemas (plain `GRANT` SQL statements referencing the service principal's client ID in backticks). Verified working end-to-end with an authenticated request, then stopped (`databricks apps stop <name>`) — an App consumes compute continuously while running, unlike a one-time job submission, so stop it between demonstrations and restart with `databricks apps start <name>`.

The notebook never drops an existing schema or table. Confirm schema names before running. The same source normalization function runs locally and in Databricks.
